# 建绘通生产部署检查（2026-10-18）

## 结论与范围

项目已具备较完整的创作功能、登录保护和部分失败恢复机制，但尚不满足直接向公网开放、供不可信用户使用的生产要求。建议先完成安全阻断项，再以单机、单进程、受控团队方式部署试运行；扩展为公共或商业服务需要进一步完成隔离、任务调度、容量及成本控制。

本次检查覆盖 Python 后端及服务模块、前端脚本与依赖、认证、数据访问、Agent、媒体处理、测试和部署资料。没有修改业务代码或现有业务数据库，没有调用收费模型接口。隔离性验证在临时数据库中完成。未检查真实服务器、云账号、域名、网络及供应商生产配置；不是完整渗透测试，也没有逐个页面进行浏览器验收。

- 另一个错误来自 `test_sidebar_metadata.py:74`，创建接口响应没有预期的 id。应先检查响应状态及响应体，再修复业务或测试。
- 单独复核 `test_agent_runtime.py`：24 个测试全部通过，包含模拟供应商的完整制作流程与真实本地 FFmpeg 合成；这不替代全量回归修复，也不代表真实供应商联调通过。
- `public/` 下所有顶层 JavaScript 文件的 `node --check` 均通过。
- 直接运行三个前端测试脚本 `content_errors.test.mjs`、`canvas_groups.test.mjs`、`agent_canvas_inputs.test.mjs` 均通过。

- `npm audit --json` 因 npm registry DNS 解析失败未完成，不能得出依赖安全的结论。
- 当前目录没有 `.git` 元数据，无法检查历史提交中的密钥、实际跟踪文件及分支发布状态；`.gitignore` 存在且排除了 data、outputs 和环境文件。

## P0：公网开放前必须处理

### 1. 私有对话的权限可以通过通用任务接口绕过

证据：`conversation_service.py:77` 对对话做所有权检查，但 `app.py:1955` 的任务列表和 `app.py:2198` 的单任务读取没有相同检查。

临时数据库实测：B 用户读取 A 的 `/api/conversations/{cid}` 返回 404；读取 `/api/tasks?project_id={cid}` 返回 200，并包含 A 的提示词；读取对应 `/api/tasks/{tid}` 同样返回 200。

整改：定义团队共享与用户私有资源的统一授权规则，对列表、详情、生成、重试、缓存、下载和删除都检查资源归属；不能只在对话页面路由检查。共享素材仍可保留，但应明确告知哪些生成内容会进入共享素材库。

验收：账号 B 无法通过任何任务或媒体衍生接口读取或操作 A 的私有内容；授权的团队共享资源按规则可访问。

### 2. 默认账号的初始凭据固定，缺少账号生命周期管理

证据：`auth_service.py:28` 固定了两个种子账号的密码哈希，`tests/test_auth.py:122` 包含与预设登录对应的明文测试凭据。虽然数据库使用 PBKDF2，固定初始凭据仍不适合生产。

整改：部署时创建独立管理员并设置随机初始密码或通过一次性初始化流程设置；生产环境拒绝使用默认种子凭据。补充修改密码、管理员重置、停用账号及失效全部会话的能力。测试使用临时生成的独立凭据。上线前替换已有默认账号密码。

### 3. 成员可以修改模型配置，模型出站请求存在 SSRF 边界缺口

证据：普通 user 账号向模型注册接口提交指向 `http://127.0.0.1:9999` 的配置，实测返回 201；`app.py:463` 的校验主要限定 URL 形式，没有限制内网地址；`app.py:920` 使用 `urlopen` 发送带 API Key 的请求并默认处理重定向。

此外 `app.py:1911` 的“从任务保存素材”远程下载分支只校验 HTTP(S)，没有复用 `video_service.py` 中的公网地址与重定向校验。即使正常缓存下载拒绝内网地址，这个后续入口仍需要统一防护。

整改：模型配置管理限制为管理员或专门权限；生产默认使用 HTTPS 和可配置的供应商白名单；禁止环回、私网、链路本地及云元数据目标；明确内部模型网关的受控例外。统一所有下载入口的防护，禁止携密钥跨源重定向，限制响应大小和总耗时，配合网络出站规则。DNS 检查到连接建立之间的重绑定风险也需考虑。

本次仅验证了危险配置可保存和相应代码路径，没有请求真实内网或云元数据接口。

### 4. 当前依赖存在已公告漏洞

本地 FastAPI 为 0.115.6，Starlette 为 0.41.3。FastAPI 的包元数据要求 Starlette >=0.40.0,<0.42.0，因此不能仅强行提高 Starlette 版本。

Starlette 0.41.3 位于以下官方公告的影响范围：

- [FileResponse Range 解析拒绝服务 GHSA-7f5h-v6xp-fcq8](https://github.com/Kludex/starlette/security/advisories/GHSA-7f5h-v6xp-fcq8)，公告修复版本为 0.49.1。项目使用 StaticFiles/FileResponse，包括公开登录静态资源。
- [multipart 大文件解析拒绝服务 GHSA-2c2j-9gv5-cj73](https://github.com/Kludex/starlette/security/advisories/GHSA-2c2j-9gv5-cj73)，公告修复版本为 0.47.2。项目有媒体上传入口。

整改：整体升级到兼容且仍受维护的 FastAPI/Starlette 组合，运行回归，再对 Python、npm、手动 vendored 前端库和 FFmpeg 做完整漏洞扫描。上述修复版本只是两个公告的门槛，不表示它们是截至检查日的完整安全基线。

## P1：正式运行需要补齐

### 5. 可重复的部署与反向代理配置

仓库未发现 Dockerfile、Compose、systemd 服务或 CI 工作流。`server.js` 启动 Uvicorn 并绑定 127.0.0.1，作为同机反向代理的后端可以使用；容器部署需要另外设计监听和网络。

至少补充一种可复现的部署方式，包括：固定 Python/Node 运行时、依赖安装、独立持久化目录、非 root 账号、自动重启、优雅停止、日志轮转、版本发布和回滚。

反向代理需要 HTTPS、正确转发 Host/协议/来源 IP、仅信任实际代理地址、请求体及超时限制。当前同源校验和 Secure Cookie 都依赖请求 URL 的协议；代理配置错误可能导致写操作 403、Cookie 未标 Secure 或登录限流错误聚合。按部署域名配置可信 Host、CSP/HSTS 等策略，并保留当前同源嵌入画布需求。

### 6. 后台任务容量、恢复与成本控制

证据：图片和音频分别用 Semaphore(2) 限制执行，但每次请求仍新建后台线程；视频和 Agent 也使用 daemon 线程，没有全局容量上限。锁、活动任务集合、任务调度均位于进程内。运行文档已明确要求单 worker。

短期：强制单 worker，增加有界队列、按账号及全局的在途任务上限、生成限流、FFmpeg 并发及 CPU/内存限制、排队容量提示和优雅停机。不能通过增加 worker 直接扩容当前实现。

中长期：将模型任务和 FFmpeg 作业移到独立 worker，以持久化队列和数据库任务租约保证同一任务只有一个执行者；补充心跳、超时、重启恢复和结果未知状态。

现有请求去重能减少重复点击，但视频供应商 POST 成功、任务号尚未落库时进程崩溃，仍可能无法确认结果。需要尽量使用供应商幂等标识或对账机制，不能声称已实现端到端恰好一次计费。

补充每账号用量、每日上限、单次操作成本上限或可执行数量上限，以及管理员总开关。无需等到供应商能提供精确费用后才开始限制资源使用。

### 7. 数据库和媒体的备份、恢复、迁移及清理

已有迁移前数据库快照，并使用 SQLite backup API，这是有效基础；未发现周期性异机备份、媒体备份策略、保留周期或恢复演练。

至少需要同时备份数据库与 uploads，记录可对应的备份时间点，异机保存并加密，明确可接受的数据丢失时长及恢复时长，实际演练恢复登录、项目、媒体和模型配置。

SQLite 可以用于低并发单机试运行。当前 records 表只有 id 主键，按 kind 查询并解析全部 JSON；列表没有分页，Agent 增量事件也先读取全部事件再过滤。应先补索引、分页、定向查询和容量测试；多实例及持续并发写入场景再迁移 PostgreSQL 等服务端数据库。

迁移现在发生于模块导入阶段，需逐步补充 schema/数据版本、迁移记录、发布前备份和回滚兼容策略。软删除素材的文件与历史任务数据需要基于引用的保留/回收机制，避免磁盘持续增长或误删仍被项目引用的文件。

### 8. 密钥存储和审计

模型 API Key 对前端脱敏，但通过通用 JSON 存储以可恢复明文写入数据库。部署备份与数据库读取权限都包含供应商密钥的风险。

补充独立于数据目录管理的加密密钥或 Secret 管理、服务账号最小文件权限、密钥轮换、日志脱敏和备份加密。记录谁修改模型、创建生成任务、删除项目或素材，以及供应商 request/task id，避免审计日志记录完整密钥和不必要的私人提示词。

### 9. 监控、告警与故障操作手册

当前有 Uvicorn 日志、部分存储错误日志和 `/api/health`，但 health 没有完整数据库写入就绪、任务调度或 FFmpeg 检查，也未发现业务指标和告警配置。

补充结构化日志与 request/task/run 关联 ID、存活/就绪检查、错误率与延迟、队列长度、任务失败率及耗时、供应商超时与额度错误、数据库锁等待、磁盘容量、备份失败告警。公开 health 可简化，磁盘容量和供应商配置状态等详细信息只给管理监控使用。

### 10. 测试和发布门禁

先恢复当前失败测试，区分过时测试与真实业务回归；再将后端、前端测试与语法检查接入 CI。增加跨账号授权、代理 HTTPS、上传总量/并发限制、重启恢复、供应商超时/结果未知、备份恢复和数据库迁移的关键验收。

真实供应商联调、小规模并发压测及浏览器端流程尚未在本次执行，生产前应在独立 staging 环境以受控额度验证。性能容量需要测量，不能从单元测试推算支持人数。

## 公共/商业服务的额外范围

- 用户与团队管理、邀请、明确的角色权限矩阵，以及资源归属模型。
- 若收费：套餐与额度、用量账本、退款/失败处理、供应商成本对账；支付是否需要取决于商业模式。
- 隐私说明、用户内容及声音/肖像使用约定、数据导出/删除、投诉与滥用处理。
- 当前简单关键词过滤加供应商拦截，不能作为完整的公共内容治理机制；应按目标场景设计输入、上传和输出治理。
- 若选择中国大陆服务器和对公众提供服务，另行核查实际业务和部署主体适用的备案、许可及生成内容相关要求。本次未作法律合规判断。
- README 与部分运行文档对参考素材和现有能力有过时描述；统一版本号、配置项、部署指南与排障文档。

## 推荐实施顺序

1. 修复跨账号任务访问、默认凭据、模型配置权限/SSRF 和已知依赖漏洞。
2. 修复回归测试，建立 CI 与独立测试环境。
3. 完成单机单 worker 的 HTTPS 部署、持久化、备份恢复、日志告警和全局容量/用量限制。
4. 演练发布回滚、任务中断恢复、磁盘容量不足和供应商超时后，再向受控团队试运行。
5. 根据公开服务与并发目标，推进独立任务 worker、服务端数据库、对象存储及完整团队/商业能力。
