## 检查依据和结论

该方式是集市用 iframe 打开应用，应用通过 postMessage 握手获取上下文；不是集市从后端直接调用建绘通 Agent API。SDK 本身只负责握手，不负责登录换票、模型协议转换、计费、任务回调或持久化。

建绘通已有 UI 和内部生成引擎可复用，但需要新增完整的“集市接入模式”。仅引入 aimarket.js 或把 Key 填入现有模型管理不足以完成适配。

## 提供的协议实际包含什么

- 子页面向直接父窗口发送 `{type:'aimarket:connect',version:1,requestId}`。
- 接收父窗口的 `aimarket:context` 或 `aimarket:error`；同时检查准确 origin、event.source、协议版本和 requestId。
- 上下文包括 user.id/name/accountType/workNumber/organization，agent.id/name，以及 apiKey。
- accountType 只有 group/ordinary，不是管理员权限字段；organization 只提供一个主组织对象或 null，不是完整成员与授权清单；agent.id 是应用身份，不是模型 ID。
- Key 约定仅保存在当前会话内存，不得展示、记录或持久化。示例没有将 Key 发送给应用后端，而是直接从浏览器调用集市。
- 默认握手等待 15 秒，每 500 毫秒重发相同握手；不是模型请求重试或模型调用超时。
- 模型地址由开发者配置，不在上下文里；示例演示 `/v1/chat/completions`、Bearer Key 和一个示例文本模型。
- 示例在 pagehide 时取消等待/当前 fetch，并清空上下文；中止请求不等于撤销供应商任务或计费。

## 后端认证是当前协议的关键待补项

浏览器 SDK 校验父页 origin/source 是必要的消息校验，但建绘通后端看不到原始 MessageEvent。浏览器将 `{user,agent,apiKey}` 转发给后端时，HTTP 请求中的用户字段仍可以由客户端修改。

SDK 对 `apiKey` 只检查字符串以 sk- 开头；这不是服务端身份核验。即便某 Key 能成功调用模型，如果平台没有提供 Key 与 user/agent/organization 的权威绑定，也不能据此授权读取相应用户的历史项目。

因此需要平台支持签名登录票据、一次性授权码或可信的身份查询接口。若平台已有此接口，只是目录中未包含文档，则补接该接口即可；不能从这三个文件推断平台不存在该能力。

## 推荐运行链路及可选分支

推荐保留建绘通现有后端执行 Agent 与 FFmpeg 的结构：集市 iframe → 前端 SDK 握手 → 建绘通后端向平台核验身份 → 建绘通会话及用户映射 → 会话绑定的模型凭据解析 → 后台任务 → 按归属授权的媒体结果。

此方案前提是平台允许应用后端使用该专用 Key。SDK 的“当前会话内存”约定不能被解释成允许将 Key 写数据库、Redis 持久化或任务正文。若允许后端使用，应用后端也只能按约定临时保存并清理，不记录请求体、上下文或密钥。

若平台要求 Key 只能留在浏览器，则必须走浏览器模型执行通道：后端生成待执行步骤，当前前端调用模型，再回传结果。需要新增结果验证、任务回执、重连和暂停机制，页面关闭后无法保证继续执行新模型请求。它比现有后端运行结构改动更大；本地 FFmpeg 仍可保留在服务端。

无论选择哪条分支，用户身份后端核验和数据隔离都需要完成。

## 容易遗漏的细节

1. 当前已经有同源的“对话→嵌入画布”通信。外层集市接入和内部画布应使用不同职责的消息；内部画布不要直接向外层集市握手，因为 SDK 检查的是直接父窗口。frame-ancestors 对嵌套层级需允许实际祖先链。
2. 集市与建绘通不同 origin 不一定跨 site。应根据最终域名、协议和端口分别判断 postMessage、Cookie 和同源校验，不能一概通过修改 SameSite 解决。
3. 如果使用 Authorization Header 调用业务 API，img/video/audio 的普通 src 请求不会自动携带同样的自定义 Header；应设计可用的媒体授权方案，保留视频 Range 播放能力，不在媒体 URL 放平台 Key。
4. 子页面 fetch 自身后端并不因为被 iframe 嵌入就变成“从集市域名请求后端”。不要为了接入把全部 CORS 和写接口 Origin 校验放开；浏览器直调集市模型接口则需要集市支持应用 origin 的 CORS。
5. localStorage 中 `jht.agent.lastRun` 目前未按账号命名空间区分。外部用户切换时需隔离恢复指针和清理内存状态；Key 及完整 context 都不能进入浏览器持久化存储。
6. 页面关闭、取消 fetch、暂停 Agent 和撤销供应商任务是不同动作。平台没有明确撤销接口时，界面不能宣称停止计费。
7. 换 Key 后查询旧视频任务可能涉及凭据归属。需要确认重新握手得到的 Key 是否有权查询旧任务，并在过期前将已生成结果安全缓存到建绘通。
8. SDK 没有定义 ready/progress/result/resize 等事件；回传任务进度、将成片加入另一个系统的素材库、自动调整 iframe 高度或单点退出都是额外协议需求，不应假定已经支持。

## 需要平台补充或确认的契约

- 后端可验证的身份票据/授权码/Key 身份查询接口，以及 user、agent、组织、scope、过期与撤销规则。
- 是否允许应用服务端转发和临时使用专用 Key；浏览器与服务端分别有哪些访问限制。
- 文本、图片、视频、音频可用模型、路由、鉴权头、参数、响应、错误码和异步查询协议。
- Key 的有效期、刷新方式、每次进入是否换 Key、跨会话查询旧任务权限以及额度归属。
- 最终集市 origin、应用域名关系、父 iframe 的 sandbox/allow/referrer 配置、下载/全屏/剪贴板权限。
- 是否需要平台统一退出、任务结果回传或成片资产入库；若需要，提供相应协议。

## 建议实施顺序与完成标准

1. 先确认身份验证、Key 可否供后端使用、四类模型协议，避免在错误的执行架构上开发。
2. 完成嵌入入口、握手、后端身份核验、本地用户映射与会话方案，做到从集市进入不再手动登录建绘通。
3. 完成工作区/任务/媒体隔离，以及会话凭据解析，做到两用户同时生成不会串数据和 Key。
4. 逐模态接入并做功能门控，所有 Agent 子调用均使用该任务的授权凭据。
5. 补齐 Key 失效与离开/刷新页面后的长任务处理，并验证播放、下载、上传及内部画布。
6. 在真实平台 iframe 中验证完整制作与恢复流程，再按一般生产部署报告完成运维准备。
