# 视频参考图片提交体积优化

版本：`video-reference-compression-20261031-1`。

大图片、多图片此前直接按原文件 Base64 编码提交，编码后约增加三分之一体积，容易增加上传和网关处理时间。此次在发送视频生成请求前生成参考图副本，素材库原文件与原分辨率不变。

## 处理规则

- 仅处理视频请求中的本地图片和道具图片，涵盖画布、首页和 Agent 共用的服务端提交链路；图片生成请求继续使用原参考图。
- 图片最长边不超过 1920 像素，不放大、不裁切。单张目标约 1 MiB，JPEG 依次尝试 88/82/76 质量；仍较大时按比例缩小，最长边最低 768。1 MiB 是优化目标，透明图片等特殊内容可能超过目标。
- 小于等于 1 MiB、最长边不超过 1920 且方向正常的图片保留原始字节。修正 EXIF 方向；有透明通道的副本用 PNG 保存。不同图片的副本格式可以不同，请求 MIME 与实际格式一致。
- 保留图片数量、引用顺序、首尾帧角色；同一张图同时用作首尾帧时也保留两次引用。
- 允许处理上传规格内的原图（最多 20 MiB），不再要求视频参考原图先小于 10 MiB。生图参考原有的 10 MiB 限制不变。
- 压缩副本采用内存缓存，以路径、大小和文件时间识别修改，最多 32 项/24 MiB，服务重启后重新生成；同时最多两个编码任务。读取缓存前仍检查素材归属和删除状态。
- 公网 URL 图片、参考视频和音频保持原协议。没有假定集市支持媒体上传 ID，也不发送未确认的压缩 HTTP 请求体。
- 任务新增 `submission_request_bytes`、`submission_reference_count`，仅记录提交体积和引用数量，不记录 Base64 内容、凭据或签名链接。JSON 使用紧凑序列化。

优化会减少参考副本中的高分辨率细节；原图保留。实际效果取决于图片内容与模型对细节的需求。此次减少请求体积，不保证消除网络中断或供应商超时，也不自动重复提交未知结果的收费请求。

## 验证

5 项压缩专项测试、34 项服务商适配测试和 11 项提交回调测试通过，覆盖请求实际使用副本、原图未变、生图不受影响、首尾帧顺序、方向、透明通道、缓存与格式。

合成高噪声 2560×1440 PNG 测量：原文件 11,076,032 字节，参考副本 1,006,992 字节，减少约 90.9%；三张同规格图片 Base64 从约 42.3 MiB 降至约 3.8 MiB。这是测试样例，不能代表所有图片的压缩率。

## 服务器安装

累计包含此前画布超时状态、三角形加载、轮询闪烁、Wan 3.0、回调和视频文件恢复修复。服务器网关仍使用 `http://192.168.241.202:4091`。待现有生成任务结束，将更新包和外部校验文件上传 `/tmp`：

```bash
cd /tmp
sha256sum -c jht-video-reference-compression-20261031.tar.gz.sha256
tar -xzf jht-video-reference-compression-20261031.tar.gz
bash /tmp/jht-video-reference-compression-20261031/apply.sh
```

安装校验版本、备份并重启应用，安装后重新加载页面。压缩对安装后的新提交生效，不会自动重新提交旧的「提交结果待确认」任务。

回滚：`bash /tmp/jht-video-reference-compression-20261031/apply.sh rollback`。业务数据保留；回滚到不支持 Wan 的旧代码时，不要选择数据库中保留的 Wan 模型。
