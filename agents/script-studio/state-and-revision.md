# 跨集状态与修订

这些记录用于避免长剧本自相矛盾。简单单场写作可以用紧凑笔记；多集或多轮修改用表格、Markdown 或 JSON 均可。不要仅为形式建立庞大数据库，也不依赖额外软件。

## 1. 信息层与版本

每条重要事实记录来源：

| 来源 | 含义 | 使用要求 |
|---|---|---|
| user | 用户明确指定或明确接受 | 作为创作硬约束；修改须有新的用户指令或已授予的修订空间 |
| source | 原文可定位的事实 | 拆解时注明章节/段落；改编时可改变但必须说明新增或改动 |
| inference | 由原文推断 | 保留不确定性，不能伪装成确证 |
| proposal | Agent 提出的创作补充 | 在采用前属于方案；完整生成授权可按注明假设采用 |

版本至少区分：`draft` 草案、`current` 当前有效、`stale` 因上游修改需要更新、`archived` 保留作历史。只有当前有效版本为续写依据。用户明确接受某提案后，它可以成为创作正典，但其原始出处仍是 Agent 提案，不变成原著事实。

同一人物改名时沿用稳定 ID，例如 `C01`；同一场景、道具、规则、事实、伏笔分别用 `L01/P01/R01/F01/S01`。只在规模需要时使用 ID，不把这些编码塞进面向观众的正文。

## 2. 最小连续性账本

| 记录 | 必需内容 | 更新时机 |
|---|---|---|
| 项目要求 | 类型、集数、时长建议、结局、禁用项、预算及来源 | 收到明确新要求 |
| 人物正典 | 名称、身份、目标、弱点、资源、关系与来源 | 建立/修改设定 |
| 角色知识 | 事实、知道的人、获知集场、获知方式；观众何时知道 | 发生披露、误导或纠正 |
| 时间线 | 事件、先后、经过时长、期限、地点、原因/后果 | 每场结束或改事件顺序 |
| 道具与证据 | 道具归属、可用状态、移动、毁损、复制、证据效力 | 道具发生转移或使用 |
| 能力/制度规则 | 触发条件、范围、限制、代价、已支付代价 | 使用能力或改变规则 |
| 人物当前状态 | 伤势、情绪、关系、资源、未完成承诺 | 每集结束 |
| 伏笔与回收 | 埋点、观众可见信息、计划回收、实际回收、剩余问题 | 埋伏笔、推进或兑现 |
| 集末快照 | 本集改变；中间集记后续承接，最终集记闭环与余韵 | 每集完成 |

角色“听说”与“知道事实”分开；谣言可以错误。观众看到凶手不等于主角知道凶手。道具被烧毁后若还能出现，必须有事先支持的副本或合理重建过程。

代价用实际状态表示，不只写“代价很大”。例如规则是每次使用能力遗忘一张熟人的脸，则账本记录本次遗忘的是谁、相关角色是否知情、后续认人方式怎样改变。不可在下一集无解释恢复。

## 3. 紧凑记录示例

```yaml
project:
  version: 2
  episodes: 3
  ending: "女主找到真相，但无法恢复已支付的能力代价"
  ending_origin: user
rules:
  - id: R01
    current: "听见法器遗言后，永久遗忘一张熟人的脸"
    limitations: "只能听最后一任主人；无法凭空追问"
    origin: user
props:
  - id: P01
    name: "断剑"
    owner: C01
    available: true
    last_change: "1-2，C02交出"
knowledge:
  - fact: F01
    content: "断剑主人死前见过掌灯人"
    audience_since: "1-3"
    characters: {C01: "1-3", C02: "未知"}
setups:
  - id: S01
    planted: "1-1，掌灯人右手烫痕"
    planned_payoff: "3-2"
    status: open
episode_end:
  episode: 1
  changed: "C01获得线索，同时忘记师父的脸"
  next_obligation: "不得让C02直接知道F01；展示认人代价"
```

这是状态格式示例，不是默认故事，不应强行加入用户项目。

## 4. 局部修订与影响传播

把自然语言修改转换为五项：

1. 修改对象：哪位人物、哪条规则、哪集、哪场、哪段对白。
2. 新要求：从什么改成什么。
3. 保留项：用户强调不要动什么。
4. 授权范围：诊断建议、局部修订或整季联动。
5. 依赖：哪些后续产物使用了旧事实。

按依赖传播：

`要求/原文解释 → 正典设定 → 分集事件 → 场次动作与对白 → 集末状态 → 后续集`。

仅修改措辞而不改事实时，停止在该段。修改角色知道事实的时间时，沿后续对白、决策、悬念传播。修改结局时，从最后选择反查前置动机、伏笔与关键资源，不能只替换最后一段。

### 例：改变能力代价

用户说：“把遗忘一段记忆改成遗忘一张熟人的脸，其余不变。”

- 先核对原有硬约束。若结局只锁定“找到真相且代价不可逆”，新规则可保留该结局；若用户硬锁“最后忘记师父的声音”，且该损失依赖原能力代价，则“只忘脸”与“其余不变”存在冲突。指出具体冲突，给出改结局损失为脸、或保留原代价等最小取舍；不偷偷改结局，也不擅加另一种失声/失忆机制。
- 改规则 `R01`，记录旧值与新值。
- 查所有使用能力的场次，决定每次遗忘谁，并更新当前状态。
- 将“忘掉某件事”的后续台词改为与认脸障碍相符的行为。
- 保留已知事件和其他能力限制；不能顺手改变敌人或结局。
- 检查已有高潮是否依赖忘记事件；在不改变用户硬约束的范围内使用最小新安排。需要改变已锁定结局时，先解决上述取舍。
- 已写第 1 集更新为当前版本；尚未更新的第 2 集标记待修，完成修订后才能用它续写第 3 集。

## 5. 修订交付

小改直接展示替换片段，附一句改动说明。较大改动给“变更摘要、影响位置、修改稿、剩余冲突”。不必把未受影响内容再次全文输出，除非用户要求完整稿。

可以自动处理的冲突立即修复；必须改变另一个用户硬约束时，指出具体两项约束及取舍。不要通过秘密改写硬约束让一致性检查看似通过。

多轮项目保存简短变更记录：版本、请求、涉及文件/集场、检查结果。保存用户要求位置的产物，不把项目状态写入可复用 skill 的安装文件。

实际保存后重读受影响产物，逐项核对新规则的条件、限制和例外，而不只搜索旧关键词。设定梗概、人物小传、大纲、正文与续集状态可能重复描述同一规则，要检查所有引用；细则应在当前规则记录中明确保留，不只留在聊天回复。只有写入并核对过的文件才能报告为“已同步”，未完成者标记待修订。历史版本可以保留旧规则，但要与当前创作依据分开，不能声称存在未实际创建或未读取的历史记录。
